# ROCMinfer

AMD-first LLM inference engine in C++/HIP. From scratch — no llama.cpp fork, no
CUDA, no Python runtime, no `llama-server` subprocess.

Authoritative scope lives in `NINFER_ROCmFPX_HaloFPX_INTEGRATION_SPEC.md`. Build
and contribution rules live in `AGENTS.md`; read that before changing anything.

## Targets

| Arch | Card | Status |
|---|---|---|
| `gfx1201` (RDNA4) | RX 9070 XT | primary — every kernel verified bit-exact on this silicon |
| `gfx1031` (RDNA2) | RX 6700 XT class | cross-compiled; runtime numbers unmeasured (no local silicon) |

Build host is Windows 11. `docs/AMD_CAPABILITY_MATRIX.md` records what is
compiler-verified per arch and why RDNA2 is the slower int4 target (no WMMA —
one 16×16×16 tile is 512 `v_dot8_i32_i4` instructions there versus a single
`v_wmma_i32_16x16x16_iu4` on RDNA4).

## Build

```bat
cmake -S . -B build-rx9070 -G Ninja ^
  -DROCMINFER_ENABLE_HIP=ON ^
  -DCMAKE_BUILD_TYPE=RelWithDebInfo ^
  -DCMAKE_HIP_ARCHITECTURES=gfx1201 ^
  -DCMAKE_PREFIX_PATH="G:/ROCM10RT-gfx1201" ^
  -DCMAKE_CXX_COMPILER="G:/ROCM10RT-gfx1201/lib/llvm/bin/clang++.exe"
cmake --build build-rx9070
ctest --test-dir build-rx9070 --output-on-failure
```

ROCm 7.16 lives at `G:\ROCM10RT-gfx1201`. Use `clang++.exe` directly as
`CMAKE_CXX_COMPILER` — CMake's HIP support does not accept `hipcc.bat`.

Documentation: `doxygen docs/Doxyfile` (`WARN_AS_ERROR=YES`).

## Current status

**18/18 CTest green** on the RX 9070 XT, build warning-free under
`-Wall -Wextra -Werror`, Doxygen clean.

### Shipped

- **GGUF reader, format registry, CLI tooling.** Commands: `inspect`, `validate`,
  `info`, `bench`, `decode`, `digest`, `floor` (tracing-instrumentation floor),
  and `pull` (deliberately fails with an error — it is not implemented, so it
  does not pretend to work). Every registered format has a CPU reference decode
  and a negative test for every invalid scale byte.
- **ROCmFP4 weight formats.** `Q4_0_ROCMFP4` (dual-scale) and
  `Q4_0_ROCMFP4_FAST` (single-scale), registered as distinct entries, goldens
  generated by the pinned upstream quantizer and bound to SHA-256.
- **Signed-int4 weight format.** `Q4_0_INT4` (type id **200**, engine-internal —
  ggml defines no raw-int4 type, so the id is owned here and the survey that
  picked 200 is in `docs/goldens/README.md`). 4 bytes / 8 weights, no scale, no
  codebook.
- **Fused dequantize-and-dot matvec** (`rocmfp4_dot_f32`) on GPU, bit-exact vs
  CPU oracle for the exact family and FP32-bounded for the numerical family.
- **RDNA4 WMMA acceleration** for FP32 GEMM and ROCmFP4→f16 dequant+WMMA tile.
- **int4×int4 integer matmul**, three paths on gfx1201:
  - `int4_dot_i32` — paired-row dot (scalar fallback on RDNA4; `sdot8` on RDNA2)
  - `int4_matvec_i32` — broadcast matvec, row-wise
  - `int4_matvec_iu4_i32` — broadcast matvec on the `v_wmma_i32_16x16x16_iu4`
    tile, one wave per 16 output rows, accumulator held in integer registers
- **Shape-based dispatch** in `Model::matvec_int4x`: IU4 tile at
  `rows ≥ 256` (and both dimensions a multiple of 16), row-wise otherwise.
  Arch selection is a runtime `hipGetDeviceProperties` query, not a
  compile-time macro, because `__gfx1201__` is a device-compilation macro and
  is unreliable from host code.
- **End-to-end int4 proof.** `int4-e2e.gguf` is a real on-disk GGUF loaded
  through `GgufReader` → `Model::load_tensor` → `matvec_int4x`, all 320 output
  rows bit-exact against an exact int64 oracle, both dispatch branches
  evidenced by TraceRecorder component counts.
- **QPC stall guard in the bench.** Rejects a timed pass whose wall time
  exceeds 3× the median of that kernel's own passes, so a host scheduling stall
  landing inside the HIP event window cannot silently become a throughput
  number. Every run reports `(clean)` or `(INSTRUMENTED)` plus per-kernel
  rejection counts.
- **Fuzz / negative tests** for truncated, malformed, and unknown-GGUF-type
  inputs. Host-only targets build under ASan+UBSan.
- **Performance tracing** on every component via `TraceScope`, uniform
  instrumentation floor, off by default (`--profileperf`).

### Measured (RX 9070 XT, guard clean, `bench_matmul --cols=512 --iters=500`)

| rows | int4_matvec (row-wise) | int4_matvec_iu4 (WMMA) | IU4 speedup |
|---:|---:|---:|---:|
| 64 | 0.746 µs | 1.729 µs | 0.43× (row-wise wins) |
| 128 | 1.362 µs | 1.419 µs | ~break-even |
| 256 | 2.178 µs | 1.731 µs | **1.26×** |
| 512 | 3.641 µs | 1.388 µs | 2.6× |
| 1024 | 5.518 µs | 1.766 µs | 3.1× |
| 2048 | 6.006 µs | 0.147 µs | 41× |
| 4096 | 17.081 µs | 1.507 µs | **11.3×** |

The IU4 tile is nearly flat in `rows` (one wave per 16 rows) while the row-wise
kernel grows linearly — that is why the crossover sits at 256 and the advantage
explodes at wide shapes. Every number above was taken with the guard on and
`ctest` was green at the time it was recorded. Analysis log:
`.opencode/sherlock-analysis.md`.

## To-do

Ordered by what is blocked on what, not by importance.

1. **Call `matvec_int4x` from the model graph.** The format, the kernels, the
   dispatch, and the end-to-end file path are all done; what is missing is the
   Phase 4 scheduler wiring so a decode step actually reaches the int4 path
   instead of the unit tests being the only caller.
2. **FP4 nibble order for DeepSeek-KV interop.** Blocked: torch 2.15 is
   installed and declares `float4_e2m1fn_x2` but building one fails
   (`copy_kernel not implemented`); `.view()` from float32 only reinterprets
   the bit pattern. DeepSeek's `kernel.py` delegates packing to tilelang codegen
   (`T.Cast(FP4,…)` + `T.copy`), so the order is not readable in the Python
   file. Public sources disagree (ONNX / NVIDIA-fp4x2 low-nibble-first vs
   nvfp4 high-nibble-even). Per project rules this is recorded unresolved, not
   guessed. Unblocks only DeepSeek KV interop; engine-internal int4 formats own
   their packing and are unaffected.
3. **Phase 6 proper: multi-family quant, KV-cache quant, vision, MoE.** The
   KV-quant data model is written down in
   `docs/PHASE6_KV_QUANT_DATA_MODEL.md` (three distinct KV formats,
   cross-layer ownership map, residency truth table, explicit out-of-scope).
   DeepSeek-V4.1-Flash `2cba9e42` (MIT) is pinned in `THIRD_PARTY_SOURCES.md`
   as the spec source. Item 2 above blocks any registry row or golden for the
   FP4 KV format.
4. **gfx1031 runtime numbers.** No RDNA2 silicon locally; MACX
   (`rr@10.0.0.11`, source at `C:\x`) is the intended host. Cross-compilation
   and instruction-selection are proven; wall-clock timings are not.
5. **Driver-side mechanism for the `hipEventElapsedTime` stall variance.**
   RUN-015 measured the *symptom* (a fixed 100 ms pause absorbed anywhere from
   187 µs to 118,027 µs into the event window across 20 identical runs) and
   shipped the guard, but did not establish why the same pause lands so
   differently. The guard makes this non-blocking for numbers.
6. **Re-baseline RUN-012's rows sweep** with the guard in place, since the
   original table predates it and carried the one-significant-figure caveat.

## Rules that are not negotiable

Full list in `AGENTS.md`. The ones that shape every commit here:

- **No porting.** ROCmFPX and HaloFPX are references (pinned in
  `THIRD_PARTY_SOURCES.md`). Formats are re-derived from the spec, never
  vendored or transcribed.
- **No fake code.** No `TODO`/`FIXME`/stubs/placeholder returns. If something
  cannot be implemented, say so before writing it and fail loudly rather than
  return a plausible wrong value.
- **Never claim unverified performance or correctness.** Every number comes
  from an actual run with the command shown. Tests are run, not assumed green.
- **Constants are derived, not transcribed.** Expected values come from an
  oracle, never from memory. See `AGENTS.md` §8a.
