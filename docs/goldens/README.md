# Golden artifacts

Format goldens are pinned to specific upstream artifacts. Regenerating a digest
here requires re-reading the exact file bytes, so a mismatch means the artifact
changed, the decoder changed, or a reader is wrong. Any of those three must be
investigated; none of them may be papered over by re-recording the value.

## Upstream-quantizer goldens

These were produced by **building the pinned ROCmFPX revision and running its
own `llama-quantize`**, which is the only way to satisfy the requirement that
goldens come from the pinned upstream quantizer rather than from this project.

Provenance:

- Source: `charlie12345/ROCmFPX` @ `fb08d7cdb67082ddda15a25e64dc7ec413afc41c`,
  recorded in `THIRD_PARTY_SOURCES.md`. The checkout was not modified.
- Build: CPU-only. The quantizer's CPU reference path is what emits ROCmFP4
  bytes, so enabling HIP could not change the output.
- Invocation: this tree takes the ftype positionally, and `--pure` makes every
  2D tensor ROCmFP4:
  `llama-quantize --pure tiny-src-f32.gguf tiny-Q4_0_ROCMFP4.gguf Q4_0_ROCMFP4 16`

| `artifacts/tiny-Q4_0_ROCMFP4.gguf` | 988,064 | `5c6edfb61dbbb50ce81ccf6b04b4ae4056b7e3ef5de0e932ca54d66601c1f45b` |

`artifacts/make_tiny_src.py` regenerates the source deterministically
(PCG64 seed 20260923) from the pinned `gguf-py`. It deliberately plants outliers
(12.5, -9.75) and an exact zero so the upstream scale search exercises both its
tail and its clip path.

## Cross-check result

`tools/crosscheck_decode.py` decodes every ROCmFP4 tensor twice: once with an
independent Python implementation of the format definition, and once with
ROCMinfer, then compares raw IEEE-754 bit patterns.

Both layouts are **bit-identical** across all 16 tensors, 1,245,184 weights per
layout:

```
=== tiny-Q4_0_ROCMFP4.gguf ===        16 tensors, all bit-identical
=== tiny-Q4_0_ROCMFP4_FAST.gguf ===    16 tensors, all bit-identical
```

Reproduce with:

```
python tools/crosscheck_decode.py build-hip/rocminfer.exe \
    docs/goldens/artifacts/tiny-Q4_0_ROCMFP4.gguf \
    docs/goldens/artifacts/tiny-Q4_0_ROCMFP4_FAST.gguf
```

Weights are exchanged as raw bit patterns rather than decimal text because JSON
has no hex-float literal and decimal formatting is not guaranteed to round-trip.
Comparing decimal output would have let a precision difference hide behind an
approximate match.

## Tensor payload digests

SHA-256 over a single tensor's packed bytes as stored in the file, produced by
`rocminfer decode <file> [tensor]`. These pin the *quantized bytes* the decoder
consumes, so a layout or offset regression is caught even if the numeric output
still looks plausible.

| Artifact | Tensor | Format | Payload bytes | Payload SHA-256 |
|---|---|---|---:|---|
| gemma-4-E2B COHERENT | `blk.0.attn_k.weight` | Q4_0_ROCMFP4 | 221,184 | `b632a3bf1e0ecd376f4b2c237a6ed76a0641ad8bc91152b4bd2d13c1abd06dcf` |
| Ornith-1.0-9b STRIX_LEAN | `output.weight` | Q4_0_ROCMFP4_FAST | 540,344,320 | `c7234c4c91ed2e75c4c79ec8c8c06bb27026e883226f452fb165ea2a96489a7b` |

| Ornith-1.0-9b STRIX_LEAN | `output.weight` | 33,554,432 | -0.234375 | 0.214844 | -2.88829e-05 |

Weight ranges are consistent with a per-block UE4M3 scale in the low
single-digit range, which is what a trained projection layer produces. A decode
yielding F16-scale magnitudes would indicate a byte-offset or layout error, not
a model property.
